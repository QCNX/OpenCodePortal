# ADR 0003: WSS Tunnel Protocol

**Date:** 2026-06-14
**Status:** Accepted

> Defines the framing format, control message protocol, streaming forwarding, and cancellation mechanism for the WSS tunnel between Agent and Gateway.

---

## Context

Portal uses a Portainer Edge Agent-style connection model: Agents **initiate** WSS connections to Gateway with zero inbound ports. All HTTP requests, WebSocket channels, and SSE streams are forwarded through this single tunnel.

Key constraints:

1. **Single WSS connection** — one long-lived WSS per Agent, no multi-channel multiplexing (no independent channel identifiers).
2. **Bidirectional transport** — control messages and data forwarding share the same connection; direction is implied by WSS send/receive.
3. **Raw HTTP semantics** — must preserve HTTP request/response integrity (status, headers, body). HTTP/2 multiplexing not supported.
4. **WebSocket frame type fidelity** — OpenCode PTY uses binary frames to send `{"cursor":N}` control JSON and text frames for terminal output. All WS frames must not be uniformly converted to text.
5. **SSE streaming** — OpenCode relies on `text/event-stream` to push real-time events like `pty.exited`. These must be forwarded in chunks, not buffered entirely.

### Excluded designs

- **No standalone frame type marker** (e.g. 1-byte direction/type identifier): WSS bidirectional already implies direction; control messages are distinguished via JSON parse.
- **No HTTP/2 or WebSocket sub-protocol multiplexing**: adds implementation complexity; single-connection throughput is sufficient.
- **No per-message channelId field**: the existing 4-byte ID is sufficient; ID ranges distinguish HTTP from WS channels.

---

## Decision

### 1. Frame types: text → control, binary → data

WSS natively distinguishes text and binary frames. Design principle:

| WSS frame type | Purpose | Payload format |
|---------------|---------|----------------|
| **text** | Control messages | JSON (`{"type":"register", ...}`) |
| **binary** | Data forwarding | `[4 bytes requestId][N bytes payload]` |

Control message JSON parsing strategy (`isControlMessage()`):

1. On frame receipt, attempt `Buffer.toString('utf8')` and `JSON.parse`.
2. If parsing succeeds and `msg.type` is in the known control message type set, handle as control.
3. Otherwise fall back to binary frame decoding.

This allows future extension: non-control JSON payloads (if any) are treated as binary data passthrough.

**Why no extra tag byte?** WSS's text/binary flag already provides frame type distinction. Adding an extra marker would be redundant with WSS and could cause ambiguity from encoding mismatches (binary-as-JSON? text-encoded binary data?).

### 2. Binary frame format

```
[0] [1] [2] [3] [4 ... N]
+--------+----------------+
| requestId (uint32 BE)    |   ← 4 bytes big-endian
+--------+----------------+
                           ↑ raw HTTP or WS tunnel payload
```

- **requestId**: Generated by Gateway in disjoint ranges: HTTP uses `1..0x7fffffff` (`nextHttpRequestId()`); WS channels use `0x80000000..0xffffffff` (`nextChannelId()`). The frame format remains unchanged.
- **payload**: HTTP mode = serialized HTTP/1.1 request/response bytes; WS channel mode = `[1-byte type tag][WS frame data]`.
- Direction is implicit — Gateway sends requests or channel_open data; Agent sends responses or WS channel data.

### 3. Control message types

| Type | Direction | Purpose |
|------|----------|---------|
| `register` | Agent → Gateway | Initial registration with token and optional instanceId |
| `registered` | Gateway → Agent | Registration result (ok/error), returns assignedId/assignedToken/gatewayId |
| `heartbeat` | Agent → Gateway | Keep-alive signal, carries sessionCount and optional opencodeVersion |
| `heartbeat_ack` | Gateway → Agent | Heartbeat acknowledgment |
| `request_cancel` | Gateway → Agent | Cancel in-flight HTTP/SSE request (browser disconnected) |
| `channel_open` | Gateway → Agent | Request to open a WS passthrough channel, carries path and headers |
| `channel_opened` | Agent → Gateway | WS channel established acknowledgment |
| `channel_error` | Agent → Gateway | WS channel open failure |
| `channel_close` | Bidirectional | Request to close a WS channel |
| `channel_closed` | Bidirectional | WS channel closed acknowledgment |
| `error` | Bidirectional | Protocol error notification |
| `shutdown` | Gateway → Agent | Gateway notifying Agent to close connection |

All control messages sent via `JSON.stringify` → WSS text frame. Both Agent and Gateway use `isControlMessage()` uniformly.

### 4. WebSocket channel tunnel framing

WS channel data adds a 1-byte tag inside the binary frame payload:

```
[requestId 4B] [0x00 | 0x01] [WS frame data]
                ↑ tag
```

- `0x00` = WS text frame
- `0x01` = WS binary frame

Tag is handled in `encodeWsTunnelPayload()` / `decodeWsTunnelPayload()`. Unrecognized tag values fall back to text during decode (legacy compatibility).

**Why is this tag needed?** OpenCode PTY uses binary frames to send cursor metadata (`0x00` + `{"cursor":N}` JSON), while terminal output is text frames. Without the tag, converting all WS frames to text would display control JSON like `{"cursor":0}` in the terminal. The tag ensures Gateway/Agent preserve the original frame type during relay.

### 5. SSE streaming

HTTP responses with `Content-Type` containing `text/event-stream` use multi-frame transmission:

1. **First frame**: HTTP response headers (`serializeResponseHeaders()`)
2. **Subsequent N frames**: body chunks from each `data` event
3. **Terminal frame**: empty payload (`Buffer.alloc(0)`)

Gateway side applies no body size limit to `text/event-stream` responses. Non-SSE responses remain single-frame buffered (entire response body assembled and sent in one frame).

**Why does SSE need special handling?** OpenCode's `/event` and `/global/event` endpoints use SSE to push real-time events (e.g. `pty.exited`). These events can arrive at any time and are long-lived. Without streaming, Agent would buffer indefinitely until timeout or OOM.

### 6. request_cancel mechanism

When the browser disconnects an HTTP/SSE proxy connection or Gateway times out an in-flight request, Gateway sends `{"type":"request_cancel","requestId":N}` to Agent.

Agent-side `cancelRequest()`:

1. Mark request as `canceled` (prevents concurrent events from triggering double cleanup)
2. Destroy `req.destroy()` and `res.destroy()`
3. Decrement `activeRequestCount` and callback `tunnel.setSessionCount()`
4. Delete from `activeHttpRequests`
5. Add requestId to `canceledHttpRequests` Set (retained 60 seconds, prevents time-delayed events from hitting deleted entries)

**Why is this needed?** When a user rapidly switches between Dashboard/instances, the browser disconnects old SSE connections without notifying Gateway. Gateway detects WS close and sends `request_cancel`; otherwise, Agent accumulates OpenCode SSE connections → `sessionCount` grows unbounded → upstream connection leak → UI stalls.

### 7. Proxy body size limits

| Boundary | Limit | Behavior |
|----------|-------|----------|
| Gateway buffered proxy request body | 50 MiB | Exceeded → 413 |
| Agent buffered non-SSE response body | 50 MiB | Exceeded → 502 (checked via both `Content-Length` declaration and actual body accumulation) |
| SSE streaming responses | Unlimited | Forward chunk by chunk, no body accumulation check |

`Content-Length` exceeding limit → reject immediately (don't start buffering). Actual body exceeding limit during transmission → interrupt and return 502.

### 8. Heartbeat

| Parameter | Value |
|-----------|-------|
| Send interval | 30 seconds (`HEARTBEAT_INTERVAL_MS`) |
| Offline timeout | 90 seconds without heartbeat (`HEARTBEAT_TIMEOUT_MS`) |
| sessionCount immediate notification | 1-second debounce: extra heartbeat sent on sessionCount change |

Heartbeat message field `sessionCount` = Agent-side in-flight HTTP/SSE proxy connection count (**not** OpenCode sessions, **not** WS PTY). Displayed as the "Active proxies" column on Dashboard.

`sessionCount` is zeroed on Agent disconnect.

## Consequences

### Positive

1. **Minimal protocol** — only text/binary distinction and the existing 4-byte ID; HTTP and WS dispatch cannot collide.
2. **SSE compatible** — multi-frame streaming ensures OpenCode `/event` etc. long connections push events correctly.
3. **Connection leak protection** — `request_cancel` ensures upstream SSE connections are released promptly on Dashboard/instance switching.
4. **Clear size boundaries** — 50 MiB limits prevent OOM; SSE exemption ensures event pushes aren't blocked.

### Negative

1. **Partitioned ID space** — callers must use the correct allocator; the high bit identifies a WS channel in logs and diagnostics.
2. **No backpressure control** — Agent's WS channels only have simple buffer limits (100 messages / 1 MiB), no flow control. GS network jitter may cause message loss.
3. **SSE terminal frame relies on payload length** — an empty Buffer serves as the stream end frame. If upstream sends an empty SSE chunk (theoretically violates SSE spec but possible), Gateway would misidentify it as stream end.
